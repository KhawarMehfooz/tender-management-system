glob: "resources/**,lang/**"
title: i18n conventions (currently English, German-only at end state)
---

The end goal is a German-only UI (see [non-negotiables.md](non-negotiables.md)), but a human
translator hasn't done the German pass yet. Until they do, we build and ship in English —
correctly wired through the translation system, so the eventual German swap is a translation
job, not a refactor.

## Current stage: English, via translation helpers
- `config('app.locale')` is `en`. Don't change it to `de` until real German translations
  exist — a `de` locale with English strings in it is confusing, not a placeholder.
- All user-facing strings go through Laravel translation helpers, keyed against
  `lang/en/*.php` (PHP array files, not `lang/en.json`). Never inline an English literal
  string directly in a Blade/Livewire view for anything the user sees.
- **Never write German text into any `lang/` file.** German translation is a deliberate human
  step done later, not something to approximate or attempt now.

## Key style: semantic keys, not English-sentence keys
- Use short, semantic, namespaced keys as the key, with the real English text as the value:
  `__('tenders.status.in_review')` → `lang/en/tenders.php`:
  `['status' => ['in_review' => 'In review']]`.
- Do not use Laravel's `__('Save changes')` sentence-as-key style — a later English wording
  tweak would silently break the key everywhere it's used, and the eventual German translator
  would be translating against unstable keys.
- Namespace by feature area (e.g. `tenders.status.*`, `tasks.validation.*`,
  `dashboard.filters.*`) so the same concept reused across the dashboard, detail page,
  export, and email shares one key instead of duplicating near-identical strings under
  separate ad-hoc keys.

## Scope
- Emails, PDF/Excel exports, and notifications are in scope too, not just on-screen UI — run
  those strings through the same translation system from the start.
- If you add a new user-facing string, add its key/value to the relevant `lang/en/*.php`
  file. Do not leave it hardcoded "to translate later" — by the time a human does the German
  pass, every string should already be a translation key.

## When the German pass happens later
- A human translator will create `lang/de/*.php` mirroring the `lang/en/*.php` key structure
  and fill in German values; the locale then flips to `de`. AI's job until then is to keep the
  `lang/en/*.php` key structure clean and complete, not to anticipate or draft German text.

## Keep customer docs in sync with feature work, and stamp timestamps
Every `docs/*.md` page starts with a `_Last updated: DD/MM/YYYY_` line directly under its H1 (e.g. `_Last updated: 28/08/2026_` — day first, matching this project's date convention, not the US MM/DD/YYYY order). Whenever a page's content changes for ANY reason — a feature change, a typo fix, a single comma — update that line to the current date in the same edit. Don't batch it as an afterthought; it happens in the same commit/change as the content edit.

Separately: when app code changes in an area a `docs/*.md` page already covers (check [[docs]]'s planned-sequence list for which page covers what), update that page's content too, in the same session as the code change — don't leave it stale for a future session to notice. This is proactive, not something to wait for the user to ask for each time. If a change is purely internal (refactor, test-only, a rule file update) with no user-visible behavior difference, no doc update is needed — only user-visible behavior changes require it.

Several feature-area rule files carry a short pointer to their corresponding doc page for exactly this reason — see [[permissions]], [[scopes-models]], [[tenders]], [[resources-tenders]], [[tasks]], [[relation-managers]], [[controllers]], [[notifications]], [[resources]], [[documents]]. If a new feature-area rule file is created later for something a doc page also covers, add the same kind of pointer then.

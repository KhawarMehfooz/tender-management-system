# Database Seeders

## DatabaseSeeder's WithoutModelEvents breaks Spatie permission seeding — fixed
`DatabaseSeeder` uses `use WithoutModelEvents;`, which mutes model events for its entire `run()` — including everything called via `$this->call()`. Spatie's permission package invalidates its cache via a `Permission`/`Role` model-saved event, so with events muted, `RolesAndPermissionsSeeder`'s `Permission::findOrCreate()` inserts rows but the cached (stale/empty) permission collection never refreshes, and the immediately-following `Role::syncPermissions()` throws `PermissionDoesNotExist`. Reproduced reliably on a clean DB via `php artisan migrate:fresh --seed`. Fixed by adding an explicit `app(PermissionRegistrar::class)->forgetCachedPermissions();` call in `RolesAndPermissionsSeeder::run()`, right after the `Permission::findOrCreate()` loop and before `Role::syncPermissions()` — scoped to the one seeder that needs it, rather than dropping `WithoutModelEvents` from `DatabaseSeeder` (which still benefits the bulk `CpvCodeSeeder`/`NutsCodeSeeder` imports). If a similar seeder ever creates permissions/roles and then immediately checks/syncs them within the same `WithoutModelEvents`-wrapped run, it needs the same explicit cache-forget call.

## DatabaseSeeder's WithoutModelEvents mutes more than the Spatie cache — Tender internal_id too
Any seeder called from DatabaseSeeder::run() (wrapped in WithoutModelEvents, which unsets the model event dispatcher for the whole nested $this->call() chain) that creates Tender rows will get `internal_id` NOT NULL violations — Tender::booted()'s `static::creating` hook that generates it never fires. Fix: at the top of the seeder's run(), call `Model::setEventDispatcher(app('events'));` to restore the dispatcher for that seeder's duration (see DemoDataSeeder::run() for the reference fix — same class of issue as the Spatie permission-cache trap already documented for RolesAndPermissionsSeeder).

## Create/complete tasks before walking a tender's status forward
Tender::changeStatusTo() gates the quality->submission transition on Tender::tasksComplete() (see [[tenders]]). Task creation in createTender() must happen BEFORE advanceTender()'s status walk, not after — otherwise the walk hits SUBMISSION while the tender has zero tasks yet (tasksComplete() is vacuously true) and the gate silently no-ops, leaving seeded tenders sitting at submission/follow-up/won/lost with open tasks once they're created afterward (confirmed via a live query: all 12 such tenders had open tasks before this was fixed). For the 4 statuses only reachable via SUBMISSION (submission/follow-up/won/lost), every created task must be forced to `done` (see REQUIRES_COMPLETE_TASKS and createTask()'s $forceDone param) — the random/overdue task-status logic only applies to earlier-phase tenders.

## Demo documents: same before/after-the-status-walk split as tasks, to demo locking
`createTender()` calls `createDocuments($tender, $team, $categories)` (see [[documents]] for the underlying model/locking rules) twice: once with all 11 `DocumentCategory` cases (minus `RESULT`/`POST_ANALYSIS` for tenders reaching SUBMISSION-or-later) BEFORE `advanceTender()`'s status walk, so a tender that reaches SUBMISSION locks them via `Tender::lockDocuments()` same as real usage, then again AFTER the walk with just `RESULT`/`POST_ANALYSIS` for tenders that did reach SUBMISSION-or-later, to demo a document created post-lock staying unlocked. Every seeded document writes a real `.txt` file to the `local` disk (`Storage::disk('local')->put(...)`, mirroring `createAttachment()`) so the download link actually works rather than 404ing on a fake path. A minority of documents (`fake()->boolean(35)`) get 2-3 versions instead of 1, to demo version history. User's explicit request, 2026-08-29.

## Demo calculations: must exist and be approved BEFORE the status walk, once M5 changed the SUBMISSION gate
Once `Tender::changeStatusTo()`'s SUBMISSION guard started requiring a fully-approved `TenderCalculation` chain instead of `tasksComplete()` (see [[tenders]] and [[milestones]]'s m5-calculation-approvals.md), `DemoDataSeeder` broke silently for every tender walked to SUBMISSION-or-later — there's no seeder test, so this wasn't caught until asked for directly; reproduced via a throwaway Pest test invoking `DemoDataSeeder` against the sqlite testing DB (safe — never run `migrate:fresh --seed` against the real dev Postgres DB to check this kind of thing).

Fix mirrors the tasks/documents ordering rule above: `createTender()` now creates the calculation (`createCalculation()`) and runs it through `approveCalculationChain()` BEFORE `advanceTender()`'s status walk, and creates `tender_team_members` rows even earlier than that (moved to right after `pickTeam()`, since `TenderCalculation::approve()`'s team-role gate needs those rows to already exist — same "create before consuming" ordering, just one more layer back than tasks/documents needed).

`ServiceCategorySeeder` now assigns each seeded category a `calculation_model` (SEC/CLN → `DEPLOYMENT_HOURS`, FM → `AREA_BASED`) and seeds its matching `ServiceCategoryCostDriverField` rows (the model-specific fields plus the 3 standard margin/risk fields every model needs, per [[milestones]]'s m5 file) — without this, `createCalculation()` has no configured category to compute against and `ServiceCategoryResourceTest`-style "unconfigured category" behavior would be the only thing ever seeded.

**Team-size trap**: tenders reaching SUBMISSION-or-later need `pickTeam()` to draw at least 6 people (owner + 5), not the usual 3-5 — `TeamRole::cases()` has 5 roles and `pickTeam()`/team-member creation assigns them round-robin over `$team->skip(1)`, so a normally-sized team can easily never produce a `FINAL_APPROVAL`-role member, silently stalling the approval chain at `MANAGEMENT_APPROVED` forever. `pickTeam()` gained `$minSize`/`$maxSize` params for this; `createTender()` passes `(6, 7)` when `$reachesSubmission`, the existing `(3, 5)` default otherwise. Tenders that don't reach SUBMISSION still get a calculation (so the tab has something to show), but only a random prefix of the 6 steps approved via `approveCalculationChain($calculation, $tender, fake()->numberBetween(0, 5))`, to demo the in-progress state too — `approveCalculationChain()` takes `?int $upToStep` (null = full chain) and stops early rather than throwing if a step's role has no eligible team member.

**Reindexing trap, found and fixed same session**: even with the size floor above, every non-SUBMISSION tender's calculation was landing with *zero* approvals — not the intended random 0-5 prefix (confirmed via a throwaway Pest seeder-invocation test: 24 of 36 seeded calculations had no approval rows at all, an outcome ~24x more common than true randomness would produce). Root cause: `foreach ($team->skip(1) as $index => $member)` (the loop that assigns `tender_team_members.functional_role`, existing since before M5) iterates `$index` starting from `Collection::skip()`'s *original* array position, not from 0 — since the owner is always `$team->first()`, the remaining members' keys start at 1, so `$index % count(TeamRole::cases())` never landed on 0 (`TeamRole::CALCULATION`) unless the team was large enough (6+) for the index to wrap back around. `CalculationApprovalStep::CALCULATION_CHECKED` is the *first* step in the chain, gated by exactly that role, so on any normal-sized team nobody could ever approve step 1, and `approveCalculationChain()`'s "stop at the first step with no eligible approver" behavior (see above) meant the whole chain silently never started. Fixed with one `->values()`: `foreach ($team->skip(1)->values() as $index => $member)` re-keys from 0 so the round-robin actually starts at `TeamRole::CALCULATION` as intended. Re-verified: zero-approval calculations dropped from 24/36 to 2/36 (the remainder plausibly true `fake()->numberBetween(0, 5)` draws of 0, expected ~4/24 at that rate). This bug predates M5 and affected general team-role assignment the whole time, not just calculations — it just had no functional consequence until the approval chain started depending on specific roles actually being assigned.

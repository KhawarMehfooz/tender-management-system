# Pages

## Custom Page canAccess() is NOT auto-wired to route/mount access
Filament\Pages\Page::canAccess() (overridden e.g. in RolesAndPermissions to gate super-admin-only pages) is only consulted by registerNavigationItems() to hide/show the nav item. It is never called automatically during routing or mount() for a plain custom Page (unlike Resource pages, which call authorizeAccess() internally). Without an explicit `abort_unless(static::canAccess(), 403);` at the top of mount() (and in any Livewire action method reachable on the page, e.g. toggle()), a user who guesses/visits the URL directly — or hits the Livewire action — bypasses the restriction entirely even though it's hidden from their nav. Always add that check yourself; don't rely on overriding canAccess() alone.

## Building a permission-matrix-style custom Page (roles x rights grid)
Pattern used by `RolesAndPermissions`: implement `Filament\Tables\Contracts\HasTable` + `use InteractsWithTable`, define `table()` with `->query(Role::query())`, a `TextColumn` for the row label, then `array_map()` over the fixed `Right` enum to spread one `ToggleColumn` per right — each with `->getStateUsing(fn (Role $r) => $r->hasPermissionTo($right->value))` and `->updateStateUsing(...)` calling `givePermissionTo`/`revokePermissionTo`. This renders with real Filament table styling (no custom Blade/Tailwind needed — avoids the [[css-filament]] theme-rebuild trap entirely). Re-check `static::canAccess()` inside `updateStateUsing` too, not just in `mount()` — per [[pages]], `canAccess()` isn't auto-wired to the Livewire action either. To shrink a `ToggleColumn` (or similar component) relative to surrounding text, `->extraAttributes(['class' => 'scale-75'])` targets the component's actual wrapper div (confirmed by reading `ToggleColumn::toEmbeddedHtml()`), not some inert outer cell — still needs `npm run build` to compile per [[css-filament]].

## RolesAndPermissionsSeeder assigns default rights per role — not a blank slate
`RolesAndPermissionsSeeder::DEFAULT_ROLE_RIGHTS` grants a default set of individually-assignable rights per role via `syncPermissions()` on seed (super-admin & department-head: all 6 rights; team-lead: see-prices/see-margins/execute-final-submission/make-bid-decision; calculation: see-prices/see-margins; concept-writer/documentation/quality-control/staff/viewer: none). This was a deliberate product decision (confirmed with the user), not inferred from idea.md — idea.md only says rights are "individually assignable, independent of role," it doesn't specify defaults. The `App\Filament\Pages\RolesAndPermissions` admin page (role x right toggle matrix, super-admin only) is where these get adjusted afterward. If you change the seeder's defaults, update `RolesAndPermissionsSeederTest`'s per-role assertions to match, and re-run `php artisan db:seed --class=RolesAndPermissionsSeeder` + `php artisan permission:cache-reset` in any already-seeded environment (seeding again doesn't retroactively fix a stale cache).
